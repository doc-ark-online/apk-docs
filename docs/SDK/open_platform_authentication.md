# 开放平台鉴权

游戏方服务端调用 233 开放平台业务接口时，需要在 HTTP 请求头中携带应用标识 `APPKEY` 和请求签名 `SIGN`。具体接口的请求方式、业务参数及响应格式，以对应接口文档为准。

## 接入准备

在 233 开发者平台获取同一应用对应的 `AppKey` 和 `AppSecret`。`AppKey` 用于填写请求头 `APPKEY`，`AppSecret` 仅用于服务端计算签名。

- 所有请求使用 HTTPS。
- `AppSecret` 仅保存在开发者服务端，不放入客户端、前端页面或公开代码仓库。
- 不在请求 URL、请求头或请求体中发送 `AppSecret`。
- 按具体接口要求提交参数，不自行修改字段名称、类型或数据结构。

## 鉴权接口

**服务地址：** `https://openapi.metaapp.cn`

**请求方式：** `GET/POST`，以具体业务接口要求为准。

请求参数按以下方式参与签名：

| 请求方式 | 参数来源 | Content-Type |
| -------- | -------- | ------------ |
| GET | URL 查询参数 | 无需为签名指定请求体类型 |
| POST | JSON 请求体，根节点应为对象 | `application/json` |
| POST | 表单请求体 | `application/x-www-form-urlencoded` |

POST 请求的 URL 查询参数不会合并进请求体签名。需要签名保护的业务参数应放在对应请求体中。对象数组规则仅适用于 JSON 请求体。

JSON 请求的 `Content-Type` 可使用 `application/json` 或 `application/json;charset=UTF-8`。表单请求使用 `application/x-www-form-urlencoded`，不要附加 `charset` 等参数；`application/x-www-form-urlencoded;charset=UTF-8` 不被接受。不要使用 `multipart/form-data` 提交本文所述的鉴权参数。

参数名称不得重复，包括 Query 参数、表单字段和 JSON 对象字段。JSON 请求体根节点必须是对象，不能直接提交数组、字符串或 `null`。

请求中至少包含一个参与签名的参数。GET 无 Query 参数，以及 JSON 请求体为 `{}`、仅包含顶层 `null` 或对象类型字段的情况，均不满足要求。无业务参数的请求，应按具体接口约定提供可签名字段。

**Headers 描述：**

每次业务接口请求都必须携带以下两个请求头。HTTP 请求头名称不区分大小写，业务参数名称区分大小写。POST 请求还需设置与请求体一致的 `Content-Type`。

| 请求头 | 描述 |
| ------ | ---- |
| APPKEY | 233 开放平台获取。在相同应用（APP）下是固定值，用来标识操作哪一个应用，不能为空 |
| SIGN   | 请求参数通过应用密钥签名运算得到的签名。每一次接口请求都会根据参数和 APP 对应的密钥进行数据签名验证，不能为空。签名规则见下文 |

## 数据签名规则

签名生成的通用步骤如下。

### 第一步

按上述请求方式提取待签名参数，将处理后的参数按参数名排序，再使用 `key1=value1&key2=value2…` 的格式拼接成字符串 `stringA`。参数名和值之间使用一个 `=`，参数之间使用一个 `&`，首尾不添加多余的 `&`。签名文本不进行 URL 编码；GET 查询参数和表单在 HTTP 传输时仍需按各自格式编码，签名使用解析后的参数名称和值。

HTTP 方法、域名、路径和请求头不自动拼入 `stringA`。不要对整个原始 JSON 请求体直接计算签名。

**特别注意以下重要规则：**

- 参数名按 UTF-16 码元的字典序升序排列；对于 ASCII 参数名，即按 ASCII 顺序排列。参数名区分大小写。
- JSON 请求体中，顶层值为 `null` 的字段不参与签名；空字符串、数字 `0` 和布尔值 `false` 均参与签名，例如 `name=`、`count=0`、`enabled=false`。表单空字符串的处理限制见示例 2。
- `APPKEY`、`SIGN` 放在 HTTP 请求头中，不加入 `stringA`。请勿把验签值同时放入查询参数或请求体；其中名为 `sign` 的字段不会被自动排除，仍按普通参数参与签名。
- 顶层字段值直接为 JSON 对象时，该字段及其内部内容不参与签名，不受本签名规则保护。
- 纯对象数组内部的嵌套对象参与签名，并递归排序字段。不要自行将顶层对象序列化后加入 `stringA`、同时仍以对象形式提交。需要鉴权保护的业务字段，不应依赖顶层对象结构；字段类型和层级必须遵循具体接口定义。

顶层字符串使用解析后的内容，不保留外层 JSON 双引号，也不保留仅用于 JSON 传输的转义表示。例如，顶层字符串中的 `\n` 在签名文本中是实际换行字符。不要删除值中的空格、换行或其他有效字符。数字使用下文约定的文本表示，布尔值使用小写 `true` 或 `false`。

#### 数组参数签名

以下分类适用于 JSON 请求体中，**顶层字段的值为数组**的情况：

- **基础类型数组**：保持元素顺序，将解析后各元素的文本表示用逗号连接，外加方括号。字符串元素不增加 JSON 双引号，例如 `["a","b"]` 的签名值为 `[a,b]`。
- **空数组**：以 `[]` 参与签名。
- **非空纯对象数组**：直接元素必须全部为 JSON 对象，按下文的对象数组规则生成签名文本。
- 数组直接包含 `null`，或直接混合对象与基础类型、对象与数组时，请求会被拒绝，返回「参数不合法」。
- 对于直接元素没有对象或 `null` 的嵌套数组，外层按元素文本拼接，其中的子数组使用其 JSON 文本，不套用纯对象数组的递归字段排序规则。

数组使用有序列表保存，签名时与实际发送时的元素顺序必须一致。纯对象数组中的对象字段允许以任意顺序提交，计算签名时再递归排序。

| 请求体 | 对应字段的签名值或结果 |
| ------ | -------------------- |
| `{"tags":["a","b"]}` | `[a,b]` |
| `{"items":[{"tags":["a","b"]}]}` | `[{"tags":["a","b"]}]` |
| `{"items":[]}` | `[]` |
| `{"items":[{}]}` | `[{}]` |
| `{"items":[null]}` | 参数不合法 |
| `{"items":[{},1]}` | 参数不合法 |
| `{"items":[{},[]]}` | 参数不合法 |
| `{"items":[{"tags":[1,null,"a"]}]}` | `[{"tags":[1,null,"a"]}]` |
| `{"items":[[1,2],["a",null]]}` | `[[1,2],["a",null]]` |

**同样的字符串数组，位于顶层字段与位于纯对象数组内部时，签名文本不同。** 顶层数组直接包含 `null` 的限制，不适用于纯对象数组内部的嵌套数组。

### 对象数组签名规则

请求体根节点为 JSON 对象，对应字段提交 JSON 数组，无需改成字符串。仅计算签名时，将纯对象数组转换为紧凑 JSON 文本，再作为该参数的 value 进入 `key=value&...` 签名流程。

1. 递归将每个对象的字段名按 UTF-16 码元的字典序升序排序（ASCII 字段名与原规则一致），包括数组元素内部的对象。
2. 所有数组保持原始元素顺序。对象内部的数组可包含对象、基础类型、嵌套数组和 `null`，并按 JSON 格式序列化。
3. 对象内部的 `null` 字段必须保留；`null`、`""`、`[]` 和 `{}` 不互相替换。
4. 不输出排版空格或换行；字符串使用 JSON 双引号，引号、反斜杠、控制字符按 JSON 规则转义。字符串本身的空格、换行不能删除。
5. 数字和字符串转义的文本表示必须与签名规则一致：数字 `1e2` 输出为 `1E+2`，小数 `1.20` 保留为 `1.20`，大整数不能先转为丢失精度的浮点数。不同语言的默认序列化结果可能不同，请通过本文固定示例核对待签名文本和签名结果。

签名使用的是解析、排序后重新序列化得到的文本，并非请求体原文，也不是简单删除原文中的空白。不同语言的默认 JSON 序列化在数字和字符转义方面可能不同，不能只做字段排序后就假定结果一致。字符串内容中的空格和换行必须保留，换行按相应转义形式输出。

应以最终发送的请求体为依据计算签名，避免签名后再次序列化时改变数字表示或精度。请对照示例验证待签名文本与最终 MD5，而不仅比较 JSON 语义是否相同。

对象字段换序不改变该签名；数组元素换序或修改元素内容后，必须重新签名。

#### 字符串转义与数字表示

生成对象数组的紧凑 JSON 文本时，字段名和字符串值使用以下转义规则：

| 字符 | 签名文本中的表示 |
| ---- | ---------------- |
| 双引号 | `\"` |
| 反斜杠 | `\\` |
| 退格、制表符、换行、换页、回车 | `\b`、`\t`、`\n`、`\f`、`\r` |
| 其他 U+0000～U+001F 字符 | `\uXXXX` |
| U+007F～U+009F 字符 | `\uXXXX` |
| U+2028、U+2029 | `\u2028`、`\u2029` |

`\uXXXX` 中的十六进制字母使用大写，例如 `\u001F`。中文等其他有效 Unicode 字符保留原字符，不额外转换成 `\uXXXX`。正斜杠 `/`、`&`、`=`、`<`、`>` 不额外转义。字符串内容中的空格和换行不能删除。

数字的文本表示会影响签名。请使用能够保留整数精度和十进制精度的处理方式：

| 请求中的数字 | 签名用数字文本 |
| ------------ | -------------- |
| `123` | `123` |
| `1.20` | `1.20` |
| `-0` | `0` |
| `-0.0` | `0.0` |
| `1e3` | `1E+3` |
| `1e-3` | `0.001` |
| `0.0000001` | `1E-7` |
| `9007199254740993` | `9007199254740993` |

不要将 `1.20` 转换成 `1.2` 后计算签名，却仍发送 `1.20`；不要先将大整数转换成可能丢失精度的浮点数。不要假定所有数字都保留原始字面形式，也不要自行把接口要求的数字字段改成字符串。涉及小数或科学计数法时，应核对转换后的文本并使用固定示例联调。

### 第二步

在 `stringA` 后追加 `&key=` 和应用的 `AppSecret`，以 UTF-8 编码计算 MD5，并将摘要输出为 **32 位大写十六进制字符串**，作为请求头 `SIGN` 的值。

```text
stringSignTemp = stringA + "&key=" + AppSecret
SIGN = MD5(UTF-8(stringSignTemp)) 的 32 位大写十六进制结果
```

`AppSecret` 使用开发者平台为该应用提供的完整值，不进行截断、补齐或额外哈希。本文测试密钥仅用于离线验证签名算法。

> 在业务接口允许的情况下，可以增加 `nonce` 参数并参与签名，使不同请求的签名有所区别。开放平台鉴权不校验 `nonce` 的唯一性或时间有效期，因此仅增加 `nonce` 不能阻止请求重放，也不能替代 HTTPS 或保护已经泄露的 `AppSecret`。`AppSecret` 应仅保存在服务端。

## 示例

示例中的 `APPKEY`、`AppSecret` 和业务参数仅用于说明签名计算。实际调用时，请替换为同一应用对应的凭据和有效业务参数，并重新计算 `SIGN`。示例 1、2 的计算使用测试密钥 `4e9bacc6e001c74f7e4761187fa46522`；示例 3～5 使用独立的计算测试专用密钥。这些凭据和签名不代表可用于线上调用的有效凭据。

### 示例 1：POST `application/json`

```bash
curl --request POST 'https://openapi.metaapp.cn/v2/user/auth' \
--header 'Content-Type: application/json' \
--header 'APPKEY: 9664891245' \
--header 'SIGN: 0857EF81F87BA34160A681D0E9FCB1C6' \
--data-raw '{"sid":"1298b012345678","uid":"Recoba"}'
```

### 示例 2：POST `application/x-www-form-urlencoded`

表单接入须满足以下约束：

- 参数名称不能重复，参数值不能是空字符串。
- 解码后的参数名称和值不能包含 `&` 或 `=`，即使传输时进行了 URL 编码。
- `Content-Type` 使用 `application/x-www-form-urlencoded`，不附加其他参数。
- 通过 HTTP 客户端正确完成表单 URL 编码。

接口允许 JSON 时，包含空字符串、特殊字符、数组或复杂结构的请求优先使用 `application/json`。

表单参数按字符串参与签名，不自动套用 JSON 字段类型转换规则。表单值 `null` 是普通字符串，不等同于 JSON 的 `null`；数组样式文本也按普通字符串处理，不执行对象数组的递归排序。

```bash
curl --request POST 'https://openapi.metaapp.cn/v2/user/auth' \
--header 'APPKEY: 9664891245' \
--header 'SIGN: 0857EF81F87BA34160A681D0E9FCB1C6' \
--header 'Content-Type: application/x-www-form-urlencoded' \
--data-urlencode 'sid=1298b012345678' \
--data-urlencode 'uid=Recoba'
```

假设传送的参数如下：

```json
{"sid":"1298b012345678","uid":"Recoba"}
```

第一步：对参数按照 `key=value` 的格式，并按照参数名 ASCII 字典序排序如下：

```text
stringA = "sid=1298b012345678&uid=Recoba"
```

第二步：拼接 API 密钥（MD5 签名方式）：

```text
stringSignTemp = stringA + "&key=4e9bacc6e001c74f7e4761187fa46522"
sign = MD5(UTF-8(stringSignTemp)) 的 32 位大写十六进制结果
```

注：`key` 为在 233 开发者平台的 `AppSecret`。

使用测试密钥 `4e9bacc6e001c74f7e4761187fa46522`，得到以下签名。示例 1、2 的参数名称和值相同，因此签名相同：

```text
0857EF81F87BA34160A681D0E9FCB1C6
```

### 示例 3：对象数组签名

请求体中的数组字段仍提交 JSON 数组，无需改成字符串。例如请求体：

```json
{
  "templateId": 10001,
  "bizTaskId": "biz_task_20260922_001",
  "scopeType": 1,
  "timeType": 1,
  "sendTime": null,
  "commonPlaceholderParams": [{ "key": "game", "value": "name" }],
  "recipients": [{
    "uid": "49bc8a59115a444bae8e019430e8587b",
    "placeholderParams": [{ "key": "nick", "value": "player" }]
  }]
}
```

得到以下 `stringA`（完整一行，不做 URL 编码）。其中：

- 顶层 `sendTime` 为 `null`，不参与签名。
- `commonPlaceholderParams`、`recipients` 为纯对象数组，按紧凑 JSON 文本作为 value。
- 对象内部字段按字典序排序（`placeholderParams` 在 `uid` 前）。

```text
bizTaskId=biz_task_20260922_001&commonPlaceholderParams=[{"key":"game","value":"name"}]&recipients=[{"placeholderParams":[{"key":"nick","value":"player"}],"uid":"49bc8a59115a444bae8e019430e8587b"}]&scopeType=1&templateId=10001&timeType=1
```

使用仅用于测试的密钥 `array-sign-test-secret`，按 UTF-8 计算：

```text
MD5(UTF-8(stringA + "&key=" + secret)) 的 32 位大写十六进制结果
```

结果应为：

```text
64DF4350C1A2EFFB4AA1C66B4F03AC78
```

对象字段换序不改变该签名；数组元素换序或修改元素内容后，必须重新签名。

### 示例 4：空值、布尔值和基础数组

请求体：

```json
{
  "tags": ["a", "b"],
  "name": "",
  "enabled": true,
  "count": 0,
  "optional": null,
  "ids": []
}
```

计算测试专用密钥为 `array-sign-test-secret`。`optional` 不参与签名；空字符串、`0`、布尔值和空数组均参与签名。

`stringA`：

```text
count=0&enabled=true&ids=[]&name=&tags=[a,b]
```

追加密钥并按 UTF-8 计算 MD5，得到：

```text
BF82069607A6DAE299EEEF35A12182A0
```

### 示例 5：中文、转义字符、小数和大整数

请求体：

```json
{
  "items": [
    {
      "text": "中文\n\"\\&=",
      "amount": 1.20,
      "id": 9007199254740993,
      "active": false,
      "remark": null
    }
  ]
}
```

计算测试专用密钥为 `array-sign-test-secret`。

`stringA`：

```text
items=[{"active":false,"amount":1.20,"id":9007199254740993,"remark":null,"text":"中文\n\"\\&="}]
```

这里 `text` 位于对象数组内部，因此 `stringA` 中的 `\n`、`\"`、`\\` 是 JSON 转义文本，分别表示换行、双引号和反斜杠。不要将这段签名用 JSON 文本再次解码。

追加密钥并按 UTF-8 计算 MD5，得到：

```text
5C9BC3B237474B74D299BE25D7290EBA
```

## 鉴权失败响应

下列鉴权相关错误使用 HTTP 状态码 **503** 返回。请同时检查响应体中的 `code` 和 `message`，不要仅根据 HTTP 503 判断为可直接重试的临时故障。

签名错误响应示例：

```json
{
  "code": 25052,
  "message": "签名验证失败",
  "data": null
}
```

| 错误码 | 含义 | 建议处理方式 |
| ------ | ---- | ------------ |
| `25002` | 服务系统异常 | 保留请求时间及错误信息，必要时联系平台支持 |
| `25003` | 业务异常 | 结合错误信息及对应接口文档排查 |
| `25004` | 参数不合法 | 检查 JSON 格式、字段类型和数组结构 |
| `25005` | 参数缺失 | 检查是否存在有效的参与签名参数 |
| `25006` | 参数头缺失 | 检查 `APPKEY`、`SIGN` 是否完整且非空 |
| `25007` | 参数头非法 | 检查请求头参数是否正确 |
| `25008` | Content-Type 不合法 | 按本文规定设置请求体类型 |
| `25050` | 账号不可用 | 检查应用状态，必要时联系平台支持 |
| `25051` | 账号不可用 | 检查 AppKey 是否正确及应用凭据是否有效 |
| `25052` | 签名验证失败 | 按下方清单逐项核对 |

业务接口的成功响应及其他业务错误，以对应接口文档为准。鉴权通过不代表业务操作一定成功。

## 签名失败排查与请求重试

出现 `25052` 时，建议依次检查：

1. AppKey 和 AppSecret 是否属于同一应用。
2. `SIGN` 是否为 32 位大写十六进制字符串，是否包含多余空格或换行。
3. 参与签名的参数是否与最终发送的参数一致。
4. 是否误将请求头、POST URL Query 参数或整个原始 JSON 文本加入签名。
5. 是否在 Body 或 Query 中额外传入了 `sign` 字段。
6. 参数名称、大小写和排序是否正确。
7. 顶层 `null` 是否已排除，JSON 空字符串是否仍保留。
8. 数组元素顺序是否一致，基础数组与对象数组是否使用了各自的转换规则。
9. 小数、大整数、中文、空格和转义字符是否发生变化。
10. 是否使用 UTF-8，是否误用了 URL 编码、Base64 或 HMAC-MD5。

排查时可以在受控的服务端环境中比较 `stringA`。不要记录或向他人提供 AppSecret，也不要记录包含密钥的 `stringSignTemp`。

重试时，参数发生变化必须重新计算签名。参数、请求头或签名错误，应先修正请求，不要直接重复重试。对创建订单、发送任务等写操作，按具体接口约定使用业务唯一标识和幂等机制；增加 `nonce` 不能代替业务幂等控制。
